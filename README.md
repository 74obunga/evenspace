# EvenSpace

EvenSpace is an event and meeting management platform with a React workspace meeting console and an offline gate scanner.

## Current state

- FastAPI application with API v1 liveness and database readiness endpoints.
- Passwords use bcrypt hashes; browser sessions use revocable opaque tokens in HTTP-only cookies with CSRF checks.
- Database-backed login throttling and server-side workspace membership checks.
- Draft and published events with public or private visibility, workspace-scoped management, and timezone-aware schedules.
- Free and priced ticket types with event and ticket capacity reservations; priced registrations remain pending until payment is confirmed.
- Retry-safe registration requests using an `Idempotency-Key`; public responses omit attendee counts.
- Separate QR-ready ticket credentials, participant ticket lookup, event-scoped gate-operator assignments, and online check-in with duplicate-scan detection.
- Event-scoped offline scanner devices with expiring/revocable bearer tokens, authorized ticket snapshots, retry-safe sync batches, and organizer-reviewed conflict resolution.
- Attendance records distinguish online and offline check-ins and preserve the client scan time alongside server receipt time.
- Private workspace events can have one meeting record with ordered agenda items, member invitations, an attendance register, revisioned minutes and approval, numbered decisions, action items with justified state changes and an append-only history, and private downloadable attachments. Meeting management is available in the React app and is limited to workspace owners and admins. Attachments are limited to 10 MB each and stored in PostgreSQL.
- Workspace admins can schedule a private physical or online meeting directly from the Meetings console. Online meetings require a secure Google Meet or Zoom link. Event and meeting records are created together in one transaction. Scheduled meetings can generate a revocable QR join link. Phone users open a public form and join the attendee list with their name, email, phone number, and staff/guest type; submissions are deduplicated by meeting and email. Online join links are revealed after registration, and workspace admins can open them from the meeting record. Organizers can review the guest contact list and record attendance after the meeting is marked held. The public form does not expose the agenda or internal meeting record before registration.
- Email notifications use a transactional outbox, workspace-overridable templates, delivery attempt history, retry backoff, and a separate SMTP worker. Registration confirmations, ticket issuance, meeting invitations, paid payment confirmations, refund-request updates, scheduled event reminders, event updates, event cancellation notices, and gate-operator assignment alerts are queued. Delivery stays pending while SMTP is not configured.
- React, TypeScript, Vite, Tailwind CSS and ZXing scanner app with an IndexedDB scan queue and cached installable application shell.
- Public participant flow to load an event by ID, register for a free ticket, display its QR credential, and retrieve an active ticket from its private credential. Ticket credentials stay in page memory and are not written to browser storage.
- Public event discovery lists upcoming published public events that remain open and have ticket capacity; participants can search, open details, and continue through the existing registration flow without needing an event ID.
- SQLAlchemy models for users, workspaces, memberships, and authentication sessions.
- Alembic migrations for the identity/workspace and session schemas.
- Local PostgreSQL and API services in Docker Compose.
- Tests for authentication, CSRF protection, login throttling, workspace isolation, event publishing, capacity-safe registration, ticket lookup/revocation, operator authorization, duplicate check-in, offline device scope, exact snapshots, batch retry, conflict resolution, scanner CORS, API liveness, and membership uniqueness.

Email verification is required for self-created accounts, with single-use links expiring after 24 hours; existing accounts were marked verified during migration. Workspace owners can invite administrators, event managers, or members; administrators can invite event managers or members. Invitations use single-use links that expire after seven days; accepting an invitation creates a verified account or adds an existing account after password verification, then signs the user in. Owners and administrators can review and revoke pending invitations. Event managers can schedule and manage events, assign gate operators, and manage scanner devices and attendance conflicts. Only owners and administrators can manage workspace membership, meetings, notification templates, and payment records. Invitation role checks are enforced by the API. Verification, password reset, and workspace invitation links are encrypted in the notification outbox, and these security email templates cannot be overridden by workspace admins. Password recovery uses single-use, 30-minute reset tokens, stores only token hashes, and revokes active sessions after a successful reset. These account emails require a valid `NOTIFICATION_ENCRYPTION_KEY` and configured SMTP. MFA and the broader organizer dashboard are not implemented yet. Meeting guest QR registration is implemented; it is available only for scheduled meetings and the QR link is revoked when the meeting is held or cancelled. Generating a replacement link invalidates the previous one. Ticket credentials are sent only when `NOTIFICATION_ENCRYPTION_KEY` is configured with a valid Fernet key; the outbox stores that content encrypted and status responses omit it. Set the same key for the API and notification worker. SMTP delivery requires configuring `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, and `SMTP_FROM_EMAIL`; workspace owners/admins can review notification status and configure workspace email templates through `/api/v1/workspaces/{workspace_id}/notifications`. Workspace managers can edit draft or published events using `PUT /api/v1/workspaces/{workspace_id}/events/{event_id}` and cancel them with `POST /api/v1/workspaces/{workspace_id}/events/{event_id}/cancel`; confirmed attendees receive the corresponding notices. Meeting attachments and the meeting frontend are implemented; browser workflow review remains for the scanner, participant ticket page, and meeting console. Ticket credentials are bearer secrets suitable for QR encoding; registration confirmation codes are not ticket or check-in credentials.

Payment work targets Kenya using M-Pesa Daraja. Paid registration reserves capacity without creating a ticket, sends an STK Push, and creates a ticket only after the server checks the Daraja transaction status. Callbacks are deduplicated, their raw payloads are not stored, and callback data alone cannot confirm payment. Public registration endpoint: `POST /api/v1/payments/public/events/{event_id}/registrations` with `Idempotency-Key` and the attendee, paid ticket type, and Kenyan phone number. Poll `GET /api/v1/payments/{payment_id}` with the same key to retrieve status and, when confirmed, the ticket credential. A repeated registration request does not send another STK prompt. Workspace owners/admins can record and view refund requests at `/api/v1/workspaces/{workspace_id}/payments/{payment_id}/refunds`; this records the request only and does not reverse funds. Actual reversal handling needs an M-Pesa API initiator, encrypted security credential, and callback endpoints. Keep `PAYMENT_PROVIDER=none` until an HTTPS callback URL is configured and the full sandbox flow is exercised. Daraja callbacks are asynchronous and Safaricom requires a publicly reachable callback; see [Daraja M-Pesa Express documentation](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate). Never place credentials in source control. Keep them in the untracked `.env` file; no ticket is issued from a browser redirect or callback alone.

## Local development

Requirements: Python 3.12+ and Docker with Docker Compose. Copy `.env.example` to `.env`, then run:

```powershell
docker compose up --build -d
docker compose exec api alembic -c alembic.ini upgrade head
```

The API is at `http://localhost:8000`; OpenAPI docs are at `/docs`. The EvenSpace app is at `http://localhost:5173`; choose **Meetings** to sign in and open the meeting console. New accounts must verify their email before signing in. SMTP delivery runs in the `notification-worker` service when configured. Generate a Fernet key for `NOTIFICATION_ENCRYPTION_KEY` (for example with Python `from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())`) and configure it identically for the API and worker before enabling ticket credential emails, password reset links, or verification links. Account emails also require SMTP configuration. `GET /api/v1/health/live` checks process liveness and `GET /api/v1/health/ready` checks the database connection.

In the Meetings console, select a workspace, enter a meeting title, type, local start/end times, and format, then choose **Schedule meeting**. Online format requires a Google Meet or Zoom URL. This creates a private event and its scheduled meeting in one transaction. Open the meeting record and choose **Generate meeting QR**; display or share the QR so attendees can submit their details. Online attendees receive a **Join online meeting** button after registration. Use a network-reachable HTTPS address for phones outside the development machine. The API equivalent is `POST /api/v1/workspaces/{workspace_id}/meetings/schedule` with `title`, `meeting_type`, offset-aware `start_at` and `end_at`, an IANA `timezone`, `meeting_mode` (`physical` or `online`), and `online_url` for online meetings.

Create an event under `/api/v1/workspaces/{workspace_id}/events`, add at least one free ticket type, then publish it. Public events can be viewed and registered at `/api/v1/public/events/{event_id}`. Registration requires a client-generated UUID v4 `Idempotency-Key`; retries return the same ticket credential. The credential is stored as a hash and can be used with `/api/v1/public/tickets/lookup`. New events default to private visibility. Workspace owners or admins can assign member gate operators, start the event, and review attendance; only those admins or assigned operators can check tickets in.

Organizers can create a scanner at `/api/v1/workspaces/{workspace_id}/events/{event_id}/scan-devices`; its token is returned once. In the scanner app, enter the event ID and token while online to cache the authorized list, then use camera QR scanning or manual code entry. Ticket codes and pending batches are kept in IndexedDB until the server acknowledges sync; the exact batch is retried if a response is lost. Pending scan conflicts can be reviewed at `/api/v1/workspaces/{workspace_id}/events/{event_id}/attendance/conflicts` and resolved through the matching `/resolve` endpoint. Device data is stored in the browser profile, so only use trusted scanner devices and remove event data after reconciliation. Apply database changes with `docker compose exec api alembic upgrade head`.

For backend tests, create a virtual environment, install `backend/requirements-dev.txt`, then run `python -m pytest backend/tests` from the repository root with `PYTHONPATH=backend`.

## Implementation sequence

1. Offline scanner path is implemented through device authorization, ticket caching, local scan queueing and retry-safe sync; browser end-to-end testing on physical devices remains.
2. Payments and refunds for Kenya via M-Pesa Daraja (paid registration, STK Push, query-gated ticket issuance, and idempotent refund request records implemented; callback URL configuration, end-to-end sandbox checkout, and provider reversal execution remain).
3. Meeting governance (agenda, invitees, attendance, minutes approval, decisions, action-item history, attachments, and workspace console); browser workflow review remains.
4. Notification outbox, SMTP adapter, configurable templates, attempts, scheduled reminders, event update and cancellation notices; organizer alerts and ticket credential email remain.
5. Public participant ticket display, public event discovery, meeting guest registration via a revocable QR/link, password recovery, email verification, workspace invitations, and restricted event-manager permissions are implemented; paid checkout activation, the broader organizer dashboard, MFA, operational hardening, and deployment guidance remain.
